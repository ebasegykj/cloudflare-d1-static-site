# PITFALLS.md — 踩坑实录（改代码前必读）

> 本文件记录本模板在真实个人站点上跑出来的事故：现象、根因、由此定下的规则。
> 这些坑不是假设，每一条都花过时间排查，因此对应的规则**不允许"优化"掉**。
>
> **给 AI 与后续维护者**：接手先通读一遍；修完任何 bug **必须回来补一条**（格式见下），
> 这是提交的一部分，不是可选项。
> 现行硬规则在 [`AGENTS.md`](../AGENTS.md)，本文是"为什么会有这些规则"的证据链。

## 补录格式

```
### YYYY-MM-DD 短标题
- 现象：（用户/监控能看到什么）
- 根因：（代码或平台层面的真实原因，不要写猜测）
- 规则：（由此定下的硬规则，与 AGENTS.md 互相引用）
- 验证：（下次怎么确认没再犯，最好是一条可执行的检查）
```

判断标准：**只写"改完不记录下次一定复发"的条目**。一次性的笔误、拼错变量名不必入库。

## 一、数据文件与路径类

### 2026-10-30 slug 被编码成字面量 %XX 文件名，中文文章详情页全挂

- 现象：bot 发布中文标题文章显示"成功"，前台详情页报「正文加载失败」；仓库里出现
  `%E6%B5%8B%E8%AF%95….js` 这类文件名。
- 根因：写仓库路径时误用了 `encodeURIComponent(slug)`。encode 只该用在**浏览器发 HTTP
  请求的 URL** 上；GitHub 的 path 里会生成字面量 `%XX` 文件名，与前台按中文 slug
  的请求永远对不上 → 404。
- 规则：**仓库文件路径永远用原始 slug；`encodeURIComponent` 只出现在浏览器请求 URL 处**
  （即 `data/content/<encodeURIComponent(slug)>.js` 这种前端请求，且只编码 slug，
  不编码 `data/` 前缀和 `/`）。
- 验证：`data/content/` 下不应有任何含 `%` 的文件名；中文标题文章的 `data/content/<slug>.js`
  能被直接命中。

### 2026-10-31 CF Pages 对不存在的路径返回 200 + 首页 HTML

- 现象：给动态 `<script>` 挂 `onerror` 判断正文是否加载成功，`onerror` 永远不触发，
  页面实际是坏的却判定成功。
- 根因：CF Pages 的 SPA 回退行为——不存在的 `.js` 也返回 `200 + text/html`，
  脚本解析失败但 `onload` 照常触发。**`try/catch` 和 `onerror` 都不能判断动态脚本成败。**
- 规则：加载后必须检查**业务变量是否真的拿到**（`(window.POST_CONTENT || {})[slug]`），
  没拿到才算失败。`assets/app.js` 的 `loadPostContent`、`assets/admin.js` 的
  `ensurePostContent` 都是这个写法。
- 验证：全仓搜 `injectScript` / `loadScript` 的调用点，之后必有"拿到没有"的检查。

### 2026-10-31 guard-data 误杀中文标题发布（quotepath 事故）

- 现象：bot 发布 2 篇中文标题文章，10 秒后被 CI 自动回滚，正文文件成了孤儿（列表里没有、
  文件还在）。
- 根因：git 默认 `core.quotepath=true`，会把中文路径输出成 `"data/content/\346\265\213…js"`。
  开头多了个引号，`^data/` 正则匹配不上 → 数据被判成"代码" → 触发"混合提交"回滚。
- 规则：**任何解析 git 文件清单的脚本，判类前必须 `git config core.quotepath false`**；
  数据判定正则用 `^data/.+\.js$`。
- 验证：`git -c core.quotepath=false diff --name-only A B` 输出的路径不带引号；
  发一篇中文标题文章不被回滚。

### 2026-10-31 同标题文章互相覆盖

- 现象：连着发两篇同标题文章，后者直接覆盖前者，搜索也分不清。
- 根因：slug 由标题生成，同名必然撞车，旧逻辑直接覆盖。
- 规则：撞车时**新条目**自动改名为 `标题 · MM-DD HH:mm`、slug 加后缀 `-MM-DD-HHmm`
  （`cnStamp()`），同批多个再追加 `-2/-3`。**老文章一个字不动。**
  这是刻意设计的行为，不要"优化"成拒绝发布或覆盖旧文。
- 验证：连发两次同标题，两条都在，新的一条副标题带时间戳。

### 2026-11-02 数据守卫回滚了合法的数据清理（两轮）

- 现象：一次"改名 + 删孤儿 + 代码收口"的提交，和一次"纯数据删孤儿"的提交，先后被 CI
  自动还原，仓库反复回到新旧文件名并存的状态。
- 根因：`guard-data.yml` 注释写的是"一次**提交**混合就回滚"，实现却比较**整个 push 区间**
  （`BEFORE..NOW` 的总 diff）。于是"文档提交 + 数据提交"搭同一趟 push 也会被整体判成混合。
  第一轮确实是自己造成的混合提交（守卫按设计回滚，没冤枉）；第二轮是纯数据提交被同趟
  push 里的文档提交连累（守卫的 bug）。
- 修复：判定改为**逐 commit**（`git rev-list` 循环 + `diff-tree` 单提交分类），只还原
  混合提交触碰过的数据文件。守卫本身保留，修的是实现。
- 规则：① 数据文件的结构性操作（改名/删除/迁移）做成**纯数据提交**，push 时**不与任何
  代码提交同行**；② 改守卫前先想清楚"判定单位是 commit 还是 push"。
- 验证：`git show --stat <sha>` 里数据提交不应出现 `assets/`、`*.html`、`wecom-worker/`
  等路径；同趟 push 混合两种提交时守卫不再误回滚。

## 二、worker / bot 类

### BUILD 常量与"push 不等于上线"

worker 改完 push 只是改了 GitHub 里的文件；**必须去 CF 控制台重贴代码（或 `wrangler deploy`）
并点部署**，且每次改动 bump 顶部 `const BUILD`，部署后访问 `/version` 核对一致才算上线。
不核对 = 永远不知道线上跑的是哪一版，排障全靠猜。

### MsgId 撞号 → 微信静默去重

- 现象：测试时同一批指令只收到裸 `success`，业务逻辑没执行。
- 根因：测试号段复用，微信按 `MsgId` 去重，重复消息直接忽略。
- 规则：**换 MsgId 号段前全文件搜一遍**（`worker.js` + `test.mjs`），确认新号段无占用。

### 企业微信的两类平台限制

- **被动回复只有 5 秒**：搜索类操作必须并行化，GitHub GET 失败重试一次；超时的回复会被
  静默丢弃。
- **主动推送受可信 IP 白名单限制**（`errcode 60020`，静默失败）：推送不可作为关键链路。
  失败时写 KV `pubfail:`，用户下一条指令开头补播一次「⚠️ 上次发布失败：原因」，播一次即销号。
  **发布失败的原因必须原样回给用户**（带首行原因），不能只说"发布失败"——用户看不到 CF 日志。
- **推论**：凡是 `waitUntil` 后台任务，结果必须同时落 KV（备份用 `bkres:<user>`，配
  「备份结果」查询命令），推送只当锦上添花。

### 免费版 Worker 单次调用限 50 次子请求（"备份D1"首备被掐断）

- 现象："备份D1"回执正常、后台任务却无结果，KV 里落的是
  `Too many subrequests by single Worker invocation`。同一份代码在小站一直正常。
- 根因：免费版每个 Worker 调用（含 `waitUntil` 后台段）最多 50 次**子请求**（fetch 出去的
  HTTP 调用）。数据量大时首备与仓库差异文件多 → blob 上传一个一发 → 总数破 50 被掐断；
  小站 D1 与仓库逐字节一致 → 零上传 → 永远碰不到。
- 规则：① 循环里发 fetch 的批处理任务必须**限批 + 支持续传**（备份用 KV 游标 `bkcurs`，
  每批 30 个 blob，回执提示"再发一次命令续传"）；② 差量设计（内容寻址跳过未变文件）
  同时是限额保护和流量优化，别改回全量；③ 估预算：建分支 5 + blob 批 30 + 提交 5 +
  微信通知 2 ≈ 42 < 50。
- 验证：`test.mjs` 的"差异文件超过 30 个 → 分批续传"用例（统计单次调用 GitHub 请求数）。
- **慢操作不能同步跑完再回**：超过 5 秒的回复会被丢弃，用户以为命令没生效。正确姿势与
  「确认」发布同模式：立即回"已安排"，任务走 `ctx.waitUntil`，结果主动推送 + 落 KV。

### 备份分支的删除同步只认数据路径

- 现象：`d1Backup` 的"D1 已删 → 备份分支同步删"循环按前缀过滤，把备份分支上的**代码文件**
  一并删光，快照不再可部署。
- 根因：按前缀区分数据/代码，在"数据目录里混着代码"时必然失效。
- 规则：删除白名单只认 `SITE_SPEC.dataDelRe`（本模板默认 `/^data\//`）。**新增数据目录
  或把代码放进数据目录时，必须同时更新 `SITE_SPEC`**，不许散落硬编码前缀。
- 验证：`test.mjs`「备份D1：分支已存在且 D1 内容有更新」用例（断言非数据文件存活）。

### CORS 预检没处理 → 浏览器后台 D1 直写全不通

- 现象：后台设置页填了 Worker 地址 + `ADMIN_KEY`，点发布报 CORS 错，请求根本没到 worker。
  用 curl 直接调却完全正常。
- 根因：worker 只在**响应**里带了 `Access-Control-Allow-Origin: *`，没处理 `OPTIONS` 预检，
  也没带 `Allow-Methods` / `Allow-Headers`。预检答不对，浏览器直接拦掉正式请求——
  响应头里的 ACAO 救不了预检。
- 规则：① 凡要给浏览器跨域调的接口，`OPTIONS` 必须在**所有路由之前**统一答（204 + ACAO +
  Allow-Methods + Allow-Headers，`x-admin-key` 这类自定义头必须列进去）；
  ② **本地 curl 测通 ≠ 浏览器能调通**。
- 验证：`test.mjs`「CORS 预检」用例 + 后台设置页「测试连接」按钮。

### flush 通用循环 vs 暂存标记：新增标记漏登记 → 整批发布失败

- 现象：微信「删」后「发」→「确认」，报"上次发布失败：仓库里找不到 `data/<标记>.js`"，
  内容退回暂存区，同批其它操作全被卡住。
- 根因：`flushPending` 开头有个通用循环——暂存标记凡是不在跳过清单里，一律当文件路径去读
  `data/<标记>.js`。新增标记（如 `ldel`）漏登记 → 文件不存在 → 整个 flush 抛错。
- 规则：① **新增暂存标记（`pushPending` 的 `file` 字段）必须同步改 flush 的跳过清单**，
  并给它写独立的 flush 分支（`worker.js` 里搜 `includes(f) continue` 可定位）；
  ② 每种暂存标记至少一条端到端用例（种 pending → 发 → 确认 → 查 `pubres` 与数据行），
  不能只测"加"不测"删"。
- 验证：`test.mjs` 对应端到端用例全绿。

### D1 API：`bind()` 之后漏 `.run()` 会静默不执行

- 现象：写入"看起来成功了"，D1 里一行没有；日志无报错。
- 根因：`prepare().bind()` 返回的是**不可 await 的语句对象**，必须接 `.run()` / `.all()` /
  `.first()` 或进 `batch()`。漏了 `await` 或漏了 `.run()`，语句根本不会发出。
- 规则：所有 D1 写操作以 `.run()` 结尾并 `await`；批量写用 `env.DB.batch()`。
  代码评审时 grep `\.bind\(` 逐个确认尾巴。
- 验证：`test.mjs` 的 D1 用例断言"写入后能读回来"，而不是只断言函数没抛错。

## 三、操作纪律类

### 用脚本写文件把 `worker.js` 覆盖成空

- 根因：图省事用 `fs.writeFileSync(p, …)` 之类的一次性脚本改大文件，参数写错直接清空。
- 规则：**改仓库内大文件一律用编辑工具的定向替换，不写一次性脚本覆盖**；
  万一覆盖，`git checkout -- <file>` 立即恢复，再想别的办法。

### 数据提交放行纪律

- pre-commit / pre-push 会拦数据文件；确需提交时用 `ALLOW_DATA_COMMIT=1`，
  **放行前必须逐条核对路径**（只允许显式列出的改名/删除，禁止顺手 `-A`）。
- 典型合法场景：初始化导入（`tools/gen-import.mjs` 产物）、批量清脏文件名。
  这两种都应该单独一趟 push，不与代码提交同行。

### 提交与提交信息

- 只 `git add` 具体代码路径；禁 `git add -A` / `git add .` / `git commit -a`。
- bash 里不能用 PowerShell 的 `-m @'…'@` here-string，会把 `@` 写进提交标题；
  多行提交信息先写临时文件再 `git commit -F <file>`。
- 网络经代理常 502 / empty reply：fetch/push 重试 2~4 次；钩子内 fetch 失败只警告不阻断。

### Pages 偶发漏掉自动部署（push 了但线上是旧的）

- 现象：push 成功、CI 绿、线上还是上一个版本；打开确认才发现。
- 根因：Pages 的 Git 集成偶发漏触发；而 CF 控制台的「重试部署」**只重跑旧提交，不拉最新代码**。
- 规则：push 后必须验证线上真的换了版本（见 `docs/SETUP.md`「部署验证」）。发现漏部署时，
  用**空提交**触发一次新构建：`git commit --allow-empty -m "chore: 触发部署" && git push`，
  然后用线上地址实际打开确认。
- 验证：以线上页面的可见改动（或 `X-Data-Source`、`/version` 之类的自证接口）为准，
  不要以"CI 绿了"为准。

## 四、外部依赖类

### 第三方图床的脆弱性

- 事实：轻量匿名图床（Telegraph 系）本体存在第三方频道/KV 里，**上游 API 曾被官方直接关闭**，
  项目被迫换上传通道。依赖链脆弱是发生过的事实，不是假设。
- 规则：① 图片优先放自有存储（仓库 `photos/`，量大后上 R2），外链图床只用于大图/临时图；
  ② 图片浏览路径**不要写 KV**（曾因每次浏览烧光每日写入额度）；
  ③ 重要图在本地或 R2 留原件。
- 想接图床时，先确认它是否支持"匿名 POST 上传并返回直链"，再改 `worker.js` 的
  `uploadToImgbed`；不支持就只支持贴链接。

### Cloudflare 免费额度速查（2026-11 核实，改动架构前先看一眼）

| 项 | 免费额度 | 本模板实际占用 |
|---|---|---|
| D1 单库 | 500MB 存储、Time Travel 7 天 | 一个个人站 < 5MB |
| D1 读写 | 500 万行读/天、10 万行写/天 | 极低（每次发布几十行） |
| Worker 子请求 | **单次调用 50 个** | 备份分批 ≤42（见上文 50 子请求条） |
| KV 写 | **1000/天** | 会话/暂存/去重，日常几十次 |
| Pages 构建 | 500 次/月 | 数据进 D1 后发布不再消耗构建 |

> 结论：**唯一容易撞墙的是"50 子请求/次"和"KV 1000 写/天"**。任何"循环里发请求"或
> "每次访问都写 KV"的设计都要先算这两笔账。
